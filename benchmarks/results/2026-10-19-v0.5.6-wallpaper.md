# Eddy TV v0.5.6 — static wallpaper A/B (2026-10-19)

**Installed launcher:** `br.eddy.tvhome` 0.5.6, versionCode 17, APK SHA-256
`8D5C15983C31F356B46D23EAFE7626C6B59E03084FE678BD9ECEE84162EFCE1C` (stored locally as
`medicoes/apks/tvhome-0.5.6.apk`), installed 2026-10-19 22:14. The installed `base.apk` hash was
checked against the stored APK.

**Question:** does the bundled static aurora wallpaper change key response, the focus spring, jank,
idle CPU or PSS on the TCL BeyondTV2?

**Short answer:** the key response and the spring duration stay at the same level, but the wallpaper
is **not free**: it adds about 9 MB of PSS and a consistent jank cost during the focus spring
(0.19% of frames with black vs 6.89% with aurora, pooled over 108 keys per condition). The wallpaper
is a smooth-motion feature; ultralight always uses black.

## Conditions

- Same TV, same session, **4 columns**, smooth motion, accessibility service off. The
  `enabled_accessibility_services` setting was empty when checked after the full battery and after
  the focused runs; no service was enabled during the session.
- The wallpaper was toggled through the real on-TV menu, item 6: black = “Papel de parede: preto”,
  aurora = “Papel de parede: Aurora”. The state was confirmed by screenshots before each condition
  (`v056-key-black-r1.png`, `v056-key-aurora-r1.png`).
- No parallel benchmarks. The runs were sequential, not randomised: full battery aurora (summary
  21:00), black (21:15); focused black r1 21:48, aurora r1 21:51, aurora r2 21:54, aurora r3 21:56,
  black r2 22:01, black r3 22:03. The sequential order is a limitation; the same key sequence and
  the same launcher state were used in both conditions.
- **Full battery:** `scripts/tcl-launcher-bench.sh` with labels `v056-wall-aurora` and
  `v056-wall-black`. It performs 5 cold starts, 10 returns to Home, 36 keys and 60 s idle.
- **Focused key probe:** `key-latency-only-v056.sh` with the same 36-key sequence as the full
  battery, labels `v056-black-r1..r3` and `v056-aurora-r1..r3`. Three series per condition give
  108 keys per condition.
- Keys are injected one at a time with 1 s between them. Response is the first frame after the key;
  movement is the continuous spring sequence. Jank is `dumpsys gfxinfo` janky frames divided by
  total frames.
- PSS and idle CPU come from the **single full-battery run per condition**, not from five
  independent batteries. They are reported as one sample per condition.

## Full battery — one run per condition

| Metric | Aurora | Black |
|---|---|---|
| Key response p50 / p95 / p99 / max | 17 / 20 / 22 / 22 ms | 18 / 21 / 22 / 22 ms |
| Spring p50 / p95 / p99 / max | 634 / 653 / 654 / 654 ms | 634 / 643 / 649 / 649 ms |
| Janky frames | 2.9% of 1364 | 0.2% of 1369 |
| Cold start p50 / max (`WaitTime`) | 404 / 525 ms | 391 / 429 ms |
| Return to Home p50 / p95 / max | 40 / 194 / 194 ms | 36 / 151 / 151 ms |
| Idle CPU, whole 4-core SoC | 15.1% | 15.1% |
| Launcher CPU, one core | 0% | 0% |
| Idle frames | 0.0 fps | 0.0 fps |
| PSS after 60 s idle | 32 MB | 23 MB |
| PSS after 10 Home returns | 30 MB | 22 MB |

The key response and spring p50 are unchanged. The cold-start and return tails differ in this single
pair (max +96 ms cold, p95 +43 ms return), but they were not repeated; treat them as indicative, not
as a proven regression. Idle CPU is identical and the launcher itself is at 0%.

## Focused key probe — three series of 36 keys per condition

| Series | Key response p50 / p95 / p99 / max | Spring p50 / p95 / p99 / max | Jank |
|---|---|---|---|
| Black r1 | 17 / 20 / 27 / 27 ms | 633 / 642 / 642 / 642 ms | 0.4% of 1372 |
| Black r2 | 17 / 20 / 21 / 21 ms | 634 / 644 / 644 / 644 ms | 0.1% of 1366 |
| Black r3 | 17 / 21 / 21 / 21 ms | 633 / 645 / 646 / 646 ms | 0.1% of 1374 |
| Aurora r1 | 17 / 19 / 31 / 31 ms | 635 / 654 / 654 / 654 ms | 11.3% of 1373 |
| Aurora r2 | 17 / 22 / 28 / 28 ms | 634 / 647 / 649 / 649 ms | 2.9% of 1365 |
| Aurora r3 | 16 / 18 / 18 / 18 ms | 635 / 646 / 658 / 658 ms | 6.5% of 1370 |

**Pooled over the three series (108 keys each):**

| Metric | Black | Aurora |
|---|---|---|
| Key response p50 / p95 / p99 / max | 17 / 20 / 21 / 27 ms | 17 / 19 / 28 / 31 ms |
| Spring p50 / p95 / p99 / max | 633 / 643 / 645 / 646 ms | 635 / 650 / 654 / 658 ms |
| Janky frames | **8 / 4112 = 0.19%** | **283 / 4108 = 6.89%** |

The response p50 is identical. The aurora tails are 7–12 ms longer on the spring, while the p50 only
moves 2 ms; that is visible mainly as a slightly less smooth animation, not as a slower key response.
The jank difference is consistent in direction in every series: black 0.1–0.4%, aurora 2.9–11.3%.
The aurora r1 11.3% is the worst outlier, but even the best aurora run (2.9%) is far above any black
run.

## Interpretation

- **The wallpaper does not change the key response p50 (17 ms) or the spring p50 (633–635 ms).**
  The full battery and the 108-key pooled run agree.
- **The wallpaper adds about 9 MB of PSS** (23 → 32 MB after 60 s idle). The bitmap itself is
  1920 × 1080 × 2 bytes = 4.1 MB in RGB_565; the rest is consistent with the GPU texture and
  compositor buffers. The TV has 2 GB, so this is not a memory-pressure problem, but it is a real
  cost.
- **The wallpaper adds a measured jank cost during the focus spring** (0.19% → 6.89% pooled).
  It is not “free”, and the v0.5.6 release notes must not say that it is.
- **Idle CPU is unchanged** (15.1% of the whole SoC, launcher 0%, 0 fps in both conditions).
- The wallpaper is enabled in smooth motion and **ultralight always uses black**. A fresh install
  starts in ultralight, so the first Home is black until smooth motion is selected. Users who want
  the lowest jank can choose “Papel de parede: preto”.

## Attempted optimisation, not adopted

A variant with `android:layerType="hardware"` on the wallpaper `ImageView` was built and tested in
two focused series (APK SHA-256
`BC89D4137AE645B69F1028A49161F2C76BCE8258ACAC51B9575C27ECDC8B65DE`):
3.4% of 1367 frames and 8.3% of 1366 frames. It did **not** remove the jank consistently, so the
final 0.5.6 build is the base build `8D5C…` above. A 1280×720 asset is the next candidate; it has
not been measured yet.
